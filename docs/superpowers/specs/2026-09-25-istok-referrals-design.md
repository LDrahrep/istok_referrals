# Istok Referrals — спецификация

Дата: 2026-09-25. Статус: на проверке у заказчика.
Исходное ТЗ: [docs/00-tz-original.md](../../00-tz-original.md). Разбор ТЗ: [docs/01-tz-review.md](../../01-tz-review.md).

## 1. Цель

Telegram-бот, через который действующие сотрудники Istok рекомендуют кандидатов на работу. Сотрудник подтверждает, что работает в компании (QR с бейджа сверяется со списком tabeli), и отправляет анкету кандидата. HR видит заявки в Google-таблице и дописывает туда свои пометки.

Главное требование — **целостность данных**: заявка не теряется, не дублируется и не портится при ручной работе с таблицей. Безопасность не приоритет.

### Принятые решения

| Решение | Почему |
|---|---|
| Бонуса за рекомендацию нет | Строгий антифрод и статусы для рекомендателя не нужны |
| Анкету целиком заполняет сотрудник | Как в ТЗ; ссылку для самого кандидата не делаем |
| Бот отдельный, на Railway | Рядом с ботом водителей; ISTOK-admin / Supabase не используем |
| Python + python-telegram-bot + gspread | Тот же стек, что у бота водителей (`istok_car_tracker`) |
| Postgres на Railway — источник правды | Данные отдельно от кода бота, бэкапы Railway |
| Google-таблица — копия для HR | HR работает в привычном инструменте, бот её чинит по базе |
| Фото на Диск загружает GAS | GAS работает от аккаунта владельца; у сервисного аккаунта нет квоты на Диске |

### Не входит в MVP

- статусы заявки и уведомления рекомендателю о судьбе кандидата;
- ссылка-приглашение для самостоятельного заполнения кандидатом;
- раздел «Мои рекомендации»;
- правка отдельного поля на экране подтверждения (только «Начать заново»);
- автопроверка «работал ли у нас» по базе tabeli;
- Mini App со сканером камеры;
- интеграция с ISTOK-admin / `friend_applications`.

## 2. Архитектура

```
Railway-проект istok-referrals
├── bot        Python-воркер, long polling, без собственного диска
└── Postgres   шаблон Railway, свой том, ежедневный бэкап
      ▲
      │ внутренняя сеть (DATABASE_URL)
      │
 bot ─┼──► Telegram Bot API          (диалоги, фото, уведомления в чат HR)
      ├──► tabeli  GET /api/attendance/bootstrap   (список активных сотрудников)
      └──► Google Sheets «Заявки»    (сервисный аккаунт, gspread)
                    ▲
                    │ колонка «Фото»
             GAS (аккаунт владельца) ──► Telegram getFile ──► Google Drive «Фото ворка»
```

### Внешние зависимости

| Система | Как используем | Если недоступна |
|---|---|---|
| Telegram Bot API | long polling, `drop_pending_updates=False` | Telegram хранит апдейты до 24 ч, бот заберёт их после рестарта |
| tabeli (AWS EC2, `http://<EIP>/api/attendance/bootstrap`, без авторизации) | раз в 15 минут забираем список активных сотрудников | Работаем по последней копии в Postgres |
| Google Sheets API | запись строк заявок, чтение колонок GAS и HR | Заявки ждут в очереди (`sheet_synced_at IS NULL`), догоняются позже |
| Google Drive (через GAS) | хранение фото для HR | Оригинал фото лежит в Postgres |

## 3. Модель данных (Postgres)

Миграции — нумерованные SQL-файлы в `referrals/migrations/`, применяются при старте бота в транзакции и записываются в `schema_migrations`.

```sql
CREATE TABLE schema_migrations (
  version     text PRIMARY KEY,
  applied_at  timestamptz NOT NULL DEFAULT now()
);

-- Копия активных сотрудников из tabeli. Строки не удаляются никогда.
CREATE TABLE employees (
  emplid     text PRIMARY KEY,              -- EMP-<uuid> (tabeli employees.id)
  qr_data    text NOT NULL UNIQUE,          -- содержимое QR (в tabeli сейчас = emplid)
  name       text NOT NULL,
  active     boolean NOT NULL DEFAULT true,
  synced_at  timestamptz NOT NULL DEFAULT now()
);

-- Сотрудники, прошедшие проверку. Один Telegram-аккаунт = один emplid.
CREATE TABLE referrers (
  tg_user_id     bigint PRIMARY KEY,
  emplid         text NOT NULL UNIQUE REFERENCES employees(emplid),
  tg_username    text,
  verify_method  text NOT NULL CHECK (verify_method IN ('qr', 'manual_id', 'admin')),
  verified_at    timestamptz NOT NULL DEFAULT now()
);

-- Состояние диалога: язык, текущий шаг, черновик анкеты.
-- Переживает рестарт бота.
CREATE TABLE sessions (
  tg_user_id      bigint PRIMARY KEY,
  language        text CHECK (language IN ('ru', 'en')),
  step            text NOT NULL,
  data            jsonb NOT NULL DEFAULT '{}',
  submission_key  uuid,                     -- выдаётся при начале анкеты
  updated_at      timestamptz NOT NULL DEFAULT now()
);

-- Заявки. Удаление в коде не предусмотрено.
CREATE TABLE referrals (
  id                   bigserial PRIMARY KEY,   -- в таблице: R-000123
  submission_key       uuid NOT NULL UNIQUE,    -- защита от двойной отправки
  first_name           text NOT NULL,
  last_name            text NOT NULL,
  phone                text NOT NULL UNIQUE CHECK (phone ~ '^\+[1-9][0-9]{6,14}$'),  -- E.164
  email                text NOT NULL UNIQUE CHECK (email = lower(email)),
  worked_before        boolean NOT NULL,
  referrer_tg_user_id  bigint NOT NULL,         -- без FK: привязку можно снять, заявка остаётся
  referrer_emplid      text NOT NULL REFERENCES employees(emplid),
  referrer_name        text NOT NULL,           -- снимок имени на момент отправки
  photo_file_id        text NOT NULL,           -- Telegram file_id (обновляется при перезаливке)
  photo_kind           text NOT NULL CHECK (photo_kind IN ('photo', 'document')),  -- как пришло: send_photo / send_document
  photo_url            text,                    -- ссылка на Диск, приходит из таблицы
  hr_data              jsonb NOT NULL DEFAULT '{}',  -- копия колонок HR: {"Статус": "...", ...}
  created_at           timestamptz NOT NULL DEFAULT now(),
  sheet_synced_at      timestamptz,             -- NULL = ещё не записана в таблицу
  hr_notified_at       timestamptz              -- NULL = уведомление в чат HR не доставлено
);

CREATE INDEX referrals_sheet_pending ON referrals (id) WHERE sheet_synced_at IS NULL;
CREATE INDEX referrals_notify_pending ON referrals (id) WHERE hr_notified_at IS NULL;

-- Оригиналы фото. Пишутся в одной транзакции с заявкой.
CREATE TABLE referral_photos (
  referral_id  bigint PRIMARY KEY REFERENCES referrals(id),
  content      bytea NOT NULL,
  mime_type    text NOT NULL,
  size_bytes   integer NOT NULL CHECK (size_bytes > 0 AND size_bytes <= 20971520),
  sha256       text NOT NULL
);
```

Повторная рекомендация кандидата, которого когда-то уже рекомендовали (даже если HR его отклонил), блокируется уникальностью `phone`/`email`. Если понадобится исключение, админ правит базу вручную.

## 4. Google-таблица «Заявки»

Лист `Заявки`, строка 1 — заголовки. Бот ищет колонки **по тексту заголовка**, а не по позиции, поэтому вставка колонок HR ничего не ломает.

| Заголовок | Кто пишет | Формат |
|---|---|---|
| `№` | бот | `R-000123` — ключ строки |
| `Дата` | бот | `YYYY-MM-DD HH:MM`, время Chicago (текст, сортируется правильно) |
| `Имя` | бот | |
| `Фамилия` | бот | |
| `Телефон` | бот | E.164 `+15551234567` (текст) |
| `Почта` | бот | нижний регистр |
| `Работал у нас` | бот | `Да` / `Нет` |
| `Рекомендатель` | бот | имя из tabeli |
| `Emplid рекомендателя` | бот | `EMP-…` |
| `file_id` | бот | служебная, колонка скрыта |
| `Фото` | GAS | ссылка на файл на Диске |
| любые другие | HR | бот не пишет, только копирует в `hr_data` |

Правила:
- Все записи бота идут с `valueInputOption=RAW`: Sheets не превращает телефон в число и не меняет формат дат.
- Колонки бота защищены в режиме «только предупреждение»: случайная правка или сортировка только этих колонок спросит подтверждение.
- Бот никогда не удаляет строки и не пишет в колонки `Фото` и HR.

## 5. Проверка сотрудника

1. `/start` → выбор языка (RU / EN) → «Пришлите фото QR с бейджа или вставьте ваш ID текстом».
2. Шаг `auth_wait_id` — **один шаг, который в любой момент принимает и фото, и текст**. Бот не уходит с этого шага, пока проверка не пройдена, и не переводит человека в запасной режим сам.
   - **Фото или файл-картинка** → декодирование QR (`zxing-cpp`, раздел 5.1).
   - **Текст** → ищем в нём `EMP-<uuid>` (без учёта регистра и пробелов по краям). Нашли → та же проверка, `verify_method='manual_id'`. Не нашли → «Это не похоже на ID. Пришлите фото QR или ID вида EMP-…», остаёмся на шаге.
   - **Другое** (стикер, голосовое, видео) → то же напоминание, остаёмся на шаге.
3. QR не прочитался → подсказка («Наклоните бейдж, чтобы не было блика, и снимите ближе. Можно прислать фото файлом — без сжатия»), остаёмся на шаге. Количество попыток не ограничено; счётчик неудач хранится в `sessions.data`.
4. После 3-й неудачи (фото не читается, ID не найден или неактивен) к подсказке добавляется кнопка «Не получается — попросить админа подтвердить». Это только вариант: человек может дальше присылать фото или текст.
   - Нажал кнопку → бот просит написать имя и фамилию, ищет совпадения среди активных сотрудников и шлёт в админ-чат карточку с кнопками «Это <имя> (EMP-…)» / «Отклонить». Нажатие создаёт `referrers` с `verify_method='admin'` и сообщает сотруднику результат (callback_data: `v:<tg_user_id>:<emplid>` — до 59 байт, в лимит 64 укладывается; отказ — `x:<tg_user_id>`). Если в tabeli два сотрудника с одинаковым именем, в карточке показываются оба.
   - Пока ждёт решения админа, человек всё ещё может прислать фото или ID — пройдёт проверку сразу, карточка у админа помечается как неактуальная.
5. Результат проверки найденного ID (одинаково для QR и текста):
   - есть среди `active = true` и не привязан → создаётся `referrers`, «Здравствуйте, <Имя>», главное меню;
   - привязан к другому Telegram-аккаунту → отказ, уведомление в админ-чат, остаёмся на шаге;
   - нет в списке или неактивен → «Не нашли вас в списке сотрудников», остаёмся на шаге (считается неудачей).
6. При каждом обращении бот проверяет, что сотрудник всё ещё `active`. Если нет — доступ закрыт.

Общее правило для всех шагов (и проверки, и анкеты): кнопки «Назад», «Отмена» и команды обрабатываются раньше, чем ввод данных шага, — нажатие кнопки меню никогда не записывается как ответ. Неподходящий ввод не сбрасывает шаг, а вызывает повторную подсказку.

### 5.1 Декодирование QR

1. Взять самый большой вариант фото из Telegram (или оригинал, если прислано файлом).
2. Повернуть по EXIF (`ImageOps.exif_transpose`), перевести в оттенки серого.
3. `zxingcpp.read_barcodes(..., formats=QRCode)`; если пусто — повторить после `ImageOps.autocontrast`.
4. Из найденных кодов взять тот, что соответствует `^EMP-[0-9a-f-]{36}$`.

Проверено на синтетике (кадр 1280×960, уровень коррекции M — как у наклеек tabeli): читаются поворот, перспектива, размытие, сильное JPEG-сжатие, тусклый свет, QR от 45 px. Не читаются блики на ≥8% площади QR — отсюда подсказка про блик и повторные попытки. Перед запуском прогнать на 5–10 реальных фото бейджей.

Команда админа `/unbind EMP-…` удаляет привязку (например, сотрудник сменил телефон).

## 6. Анкета кандидата

Шаги (на каждом есть «Назад» и «Отмена»; состояние в `sessions`):

| Шаг | Проверка |
|---|---|
| Имя | 1–50 символов: буквы (латиница/кириллица), пробел, дефис, апостроф |
| Фамилия | то же |
| Телефон | `phonenumbers`, регион по умолчанию US, должен быть валидным → E.164. Если такой уже есть в `referrals` → «Этого кандидата уже рекомендовали (R-…)», анкета прерывается |
| Почта | обязательна (как в ТЗ); регулярное выражение `^[^@\s]+@[^@\s]+\.[^@\s]+$`, приводится к нижнему регистру; дубль → как с телефоном |
| Работал у нас | кнопки Да / Нет |
| Фото ворка | фото или файл с `image/*`, до 20 МБ; в `sessions.data` сохраняются `file_id`, тип (`photo`/`document`), MIME и размер |
| Подтверждение | сводка + кнопки «Отправить» / «Начать заново» / «Отмена» |

`submission_key` выдаётся при входе в анкету и живёт в `sessions` до успешной отправки.

### Отправка

1. Скачать фото из Telegram по `file_id` (до транзакции). Не удалось → «Попробуйте ещё раз», черновик цел.
2. Транзакция:
   - `INSERT INTO referrals … ON CONFLICT (submission_key) DO NOTHING RETURNING id`. Пусто → заявка уже создана (повторное нажатие / повторная доставка апдейта) → ответить тем же успехом с существующим номером.
   - `INSERT INTO referral_photos` (содержимое, MIME, размер, sha256).
   - Сбросить черновик в `sessions`.
   - Нарушение уникальности `phone`/`email` (гонка двух анкет) → откат, «Этого кандидата уже рекомендовали».
3. После коммита: ответ «Заявка R-000123 принята», запуск записи в таблицу и уведомления HR (оба не блокируют ответ).

## 7. Фоновые задачи (PTB JobQueue)

| Задача | Период | Что делает |
|---|---|---|
| `sync_employees` | 15 мин + при старте | `GET /api/attendance/bootstrap` → из `employees[]` берём `id` → `emplid`, `qr_data`, `name`; upsert в `employees` (`active=true`); отсутствующих помечает `active=false`. **Предохранитель:** если в ответе меньше 50% текущих активных, деактивацию пропускаем и шлём алерт |
| `push_referrals` | 1 мин + сразу после отправки | Для `sheet_synced_at IS NULL`: читает колонку `№`; строки нет → дописывает, есть → обновляет колонки бота. Затем ставит `sheet_synced_at`. Если бот упал между записью и отметкой, следующий запуск найдёт строку и не создаст дубль |
| `notify_hr` | 1 мин + сразу после отправки | Для `hr_notified_at IS NULL`: шлёт в чат HR фото по `file_id` (`send_photo` или `send_document` по `photo_kind`) и данные заявки, ставит `hr_notified_at` |
| `reconcile_sheet` | 15 мин | Читает лист целиком одним запросом. Нет строки заявки → дописать. Колонки бота расходятся с базой → перезаписать ячейки. Колонки `Фото` и HR → сохранить в `photo_url` / `hr_data`. Алерты: строки с `№`, которого нет в базе; дубли `№`; отсутствие обязательного заголовка (тогда запись в таблицу останавливается) |
| `reupload_stale_photos` | 1 раз в сутки | Заявки старше 24 ч без `photo_url`: бот отправляет оригинал из `referral_photos` в админ-чат, получает новый `file_id`, обновляет базу и колонку `file_id`. GAS подхватит на следующем запуске |

Все задачи, которые пишут в таблицу (`push_referrals`, `reconcile_sheet`, `reupload_stale_photos`), берут `pg_try_advisory_lock` на время записи. Поэтому они не пересекаются ни внутри одного экземпляра бота, ни между старым и новым экземпляром во время деплоя, и две задачи не допишут одну заявку дважды. Не получили блокировку — пропускаем запуск.

Ошибки задач логируются. Повторяющийся сбой (3 запуска подряд) → алерт в админ-чат, не чаще раза в час на тип ошибки.

## 8. GAS: загрузка фото на Диск

Скрипт `gas/photos.gs`, привязан к таблице, работает от аккаунта владельца.

- Триггер по времени раз в 5 минут.
- `LockService.getScriptLock().tryLock(0)`: если предыдущий запуск ещё идёт, выходим.
- Ищет строки, где `file_id` заполнен, а `Фото` пусто. За один запуск не больше 30 строк (лимит времени выполнения GAS).
- Для каждой: имя файла `R-000123 Имя Фамилия.<расширение>`. Если файл с таким именем уже есть в папке, берём его, иначе `getFile` → скачать по `https://api.telegram.org/file/bot<token>/<file_path>` → `folder.createFile(blob)`. Пишем ссылку в `Фото`.
- Ошибка по строке → в ячейку `Фото` ничего не пишем, ставим заметку к ячейке с текстом ошибки, идём дальше.
- Токен бота и ID папки хранятся в Script Properties.

Папки на Диске (отдельно от папки с фото действующих сотрудников):

```
📁 Istok Referrals/
   📊 Заявки
   📁 Фото ворка/
```

## 9. Админские функции

Настраиваются через `ADMIN_CHAT_ID` (чат HR: уведомления о заявках, алерты) и `ADMIN_USER_IDS` (кто может выполнять команды).

| Команда / кнопка | Действие |
|---|---|
| Карточка подтверждения сотрудника | Кнопки «Это <имя>» / «Отклонить» (раздел 5) |
| `/unbind EMP-…` | Снять привязку Telegram-аккаунта |
| `/sync` | Немедленно запустить `sync_employees`, `push_referrals`, `reconcile_sheet` |

## 11. Переменные окружения

| Переменная | Назначение |
|---|---|
| `TELEGRAM_BOT_TOKEN` | токен бота |
| `DATABASE_URL` | `${{Postgres.DATABASE_URL}}` в Railway |
| `TABELI_URL` | базовый адрес tabeli, например `http://<EIP>` |
| `GOOGLE_CREDENTIALS` | JSON сервисного аккаунта (как в боте водителей) |
| `SPREADSHEET_ID` | ID таблицы «Заявки» |
| `SHEET_NAME` | имя листа, по умолчанию `Заявки` |
| `ADMIN_CHAT_ID` | чат HR |
| `ADMIN_USER_IDS` | Telegram ID админов через запятую |

Часовой пояс для отображения — `America/Chicago`, константа в коде.

## 12. Тестирование

- **Юнит-тесты (pytest):** валидация имени/телефона/почты; декодирование QR на наборе фото (чёткое, с бликом, под углом, не QR); сопоставление заголовков и расчёт расхождений для `reconcile_sheet` на фейковых данных листа; предохранитель `sync_employees`.
- **Интеграционные тесты с настоящим Postgres** (локально в Docker): миграции с нуля; двойная отправка с одним `submission_key` даёт одну заявку; дубль телефона/почты отклоняется; заявка и фото пишутся атомарно (ошибка на фото откатывает заявку).
- **Ручная проверка перед запуском:** отдельный тестовый бот из BotFather, копия таблицы, тестовая папка на Диске. Прогон: проверка по QR → анкета → строка в таблице → фото на Диске → сверка после ручной порчи строки (удалить строку, затереть ячейку, отсортировать колонку бота).

## 13. Развёртывание

1. Приватный репозиторий на GitHub, Railway-проект `istok-referrals` с автодеплоем из `main`.
2. Сервис Postgres из шаблона Railway, ежедневный бэкап.

## 14. Проверить при реализации

- Доступны ли бэкапы Railway на текущем тарифе. Если нет — добавить задачу ежедневной выгрузки `referrals` (без фото) файлом в админ-чат.
- Как Railway перекрывает старый и новый деплой у сервиса без тома: два экземпляра на long polling конфликтуют (`409 Conflict`). Идемпотентность отправки делает это безопасным, но при необходимости отключить перекрытие настройкой деплоя.
